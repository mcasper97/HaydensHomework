## 1. Identity, Household, and Device Model

- **One Firebase Auth user = one household.** There is no separate `Household`, `User`, `HouseholdMembership`, or `Profile` entity. `ctx = { uid, isAdmin }` is the sole tenancy key used by every repository module (`src/data/itemsRepository.js`, `sourceRecordsRepository.js`, `ingestionCandidatesRepository.js`, `itemCompletionsRepository.js`). `isAdmin` means "guest/local-demo profile" (routes to `localStorage` instead of Firestore) — it is **not** a privilege level.
- **Children are plain data**, not authenticated accounts: an array of `{id, name, emoji}` objects stored on the `users/{uid}` document (see `FamilyBoard.jsx`). A child has no independent Firebase credential.
- **Parent/Child separation is a client-side device lock**, not a second identity: `src/deviceMode.js` + `src/data/parentPin.js` + `src/ParentUnlock.jsx`. `deviceMode` (`"parent" | "child" | "organizer"`) and a locked `childId` are stored in `localStorage`, scoped per-browser/device, not per-account. A 4-digit PIN gates "Parent Unlock" from a locked Child-Mode device. There is **no server-side concept of "child" at all** — the same Firebase uid and the same Firestore document own everything.
- Multi-adult independent accounts (a second parent with their own login sharing the same household) do **not** exist in any form.

## 2. Canonical Obligation Model

- **File:** `src/data/itemsRepository.js`, `src/data/itemTypes.js`.
- One canonical `items` subcollection: `users/{uid}/items/{itemId}`.
- **Types** (`FORM_TYPES` in `itemTypes.js`): `assignment`, `test`, `quiz`, `project`, `school_event`, `family_event`, `study_task`, `reminder`. `chore` exists in the shared `ITEM_TYPES` vocabulary for icon/label only and is explicitly excluded from `FORM_TYPES`/`itemsRepository.js` — chores are a **separate, legacy, non-canonical model** (see §4).
- **Fields:** `type, title, childIds[], subject, academicTopic, academicUnit, preparationRequired, startDate, startTime, dueDate, dueTime, endDate, endTime, allDay, status, notes, parentItemId, sourceRecordId, schedule`.
- **Status lifecycle:** `ITEM_STATUSES = ["open", "in_progress", "completed", "cancelled"]`; `ACTIONABLE_STATUSES = {"open","in_progress"}` gates bucketing. Status is a single persistent value with no date dimension.
- **Due vs. occurrence date are separate fields** (`dueDate` vs `startDate`), matching Product Spec v2 §5.1.
- **`study_task` → assessment linkage:** `parentItemId` lets a manually-created `study_task` point at a `test`/`quiz`/`project` (`ItemForm.jsx`'s "Supports (optional)" field). This link is **never created automatically** — see §6.
- **Recurrence (added this session, reminders/events only):** `schedule: {recurring, weekdays[0-6], timeMode: "daypart"|"exact"|null, daypart, time, active}`, evaluated centrally in `src/organizer/itemBuckets.js` (`normalizeSchedule`, `isRecurringDueOn`). One canonical Item + schedule metadata — no per-occurrence Item documents are generated. Per-occurrence completion is tracked separately (`src/data/itemCompletionsRepository.js`, `users/{uid}/itemCompletions/{itemId}:{date}`), so completing "today's snack reminder" never flips the underlying Item's own `status`.
- **Test coverage:** `tests/item-buckets-recurrence.unit.mjs` (44 assertions), `tests/item-completions-repository.unit.mjs` (21 assertions), `tests/recurring-reminders.playwright.cjs` (29 assertions, full create→complete→edit→calendar round trip).

## 3. Planner / Organizer / Calendar

- **`src/organizer/ParentOrganizer.jsx`** — Today / Needs Attention (overdue) / Upcoming, full CRUD via `ItemForm.jsx`, filterable by child. Reused in three modes via props (`allowManage`, `allowComplete`): full Parent Mode, read-mostly Organizer/kiosk Mode (`OrganizerDisplay.jsx`), and (indirectly) the child's own "My Day" card.
- **`src/organizer/OrganizerCalendar.jsx`** — a **7-day horizontal strip only** (today → +6 days). There is **no Day/Week/Month/Schedule-List view** of the kind described in the older `02-PHASE-1-UX-SPEC.md` §6 and `01-PHASE-1-PRODUCT-SPEC.md` §4.1. Product Spec v2 does not require these either (§5.2 only asks for "Planner/Organizer" + "Selective Google Calendar visibility"), so this is not a v2 gap, but it is a real capability gap against the older docs.
- **`src/organizer/ChildTodayView.jsx`** ("My Day") — reads the exact same `bucketItems()`/`choresDueToday()` pure functions as the parent views, so a recurring reminder, chore, or edited due date is consistent across all three surfaces without a second copy of the data. Verified live via `tests/domain-hardening.playwright.cjs` and `tests/recurring-reminders.playwright.cjs`.
- **Single source of truth confirmed structurally:** all three surfaces call `subscribeItems(ctx, ...)` from the one `itemsRepository.js` module; none maintains its own item array.

## 4. Chores

- **Storage:** `choreTemplates` / `choreCompletions` / `chorePoints` are flat maps stored **directly on the `users/{uid}` document** (not a Firestore subcollection, not the canonical `items` model). Owned entirely by `FamilyBoard.jsx`; there is no dedicated repository module.
- **Template shape:** `{id, text, points}` only — **no schedule/weekday/interval field of any kind.**
- **"Recurrence":** `choresDueToday()` (`itemBuckets.js`) returns every template for every child, **every single day, unconditionally**. There is no daily/weekly/selected-weekday/monthly distinction — a chore is either assigned or not; if assigned, it is due every day forever. Per-day state is tracked only for *completion* (`choreCompletions[childId][dateStr] = [choreId, ...]`).
- **This is architecturally a second, independent recurrence model**, parallel to and inconsistent with the new canonical `schedule` field built for reminders this session (§2). They do not share code, and a chore cannot be scheduled for "Mon/Wed/Fri" the way a recurring reminder now can.
- Chores are excluded from `bucketItems()`/the canonical `items` collection entirely; they are projected in separately everywhere they appear.

## 5. Ingestion Pipeline and Source/Candidate Lifecycle

- **Sources implemented:** manual entry, photo/image capture (`api/extract-obligations.js`), Gmail email (`api/gmail-check-email.js`, `api/_emailExtraction.js`), linked teacher webpages (`api/_googleDocFetch.js`, `api/_htmlToText.js`, `api/_urlSafety.js`), linked Google Docs, and CSV bulk import (`App.jsx`). This **exceeds** Product Spec v2 §5.3's minimum requirement (manual + photo required; "retain substantially complete generic ingestion paths" for the rest) — all of it is retained and working.
- **`SourceRecord`** (`src/data/sourceRecordsRepository.js`, `users/{uid}/sourceRecords`): `sourceType ∈ {manual, image_capture, csv_import, gmail_email, webpage, google_doc}`, `processingStatus ∈ {captured, processing, extracted, no_candidates, failed}`. Confirmed via `tests/source-record-provenance.playwright.cjs` and `tests/photo-ingestion-guest-gate.playwright.cjs` that a failed/blocked extraction still creates a SourceRecord (`processingStatus: "failed"`) rather than silently disappearing.
- **`IngestionCandidate`** (`src/data/ingestionCandidatesRepository.js`, `users/{uid}/ingestionCandidates`): `reviewStatus ∈ {pending, rejected, approved, committed, corroborated}`. `pending → approved → committed` is a two-write sequence (`CandidateReviewModal.jsx`'s `handleApprove`): the candidate is flagged `"approved"` **before** `createItem()` runs, and only flipped to `"committed"` after `createItem()` succeeds — so a network failure between those two writes leaves the candidate at `"approved"`, never silently reverted or silently duplicated **today**, because nothing currently re-attempts an `"approved"` candidate automatically. See Gap Analysis AC-05 for the latent risk this leaves.
- **Review UI is transient, not a standing inbox.** `CandidateReviewModal.jsx`'s own doc comment: *"not the full Review Inbox (out of scope)."* It steps through exactly the candidates produced by the capture/Check-Email run that just happened. **`listIngestionCandidates()` (the repository function that would list *all* pending candidates) is exported but never called from any UI component** — confirmed via repo-wide grep. If a parent closes the modal without resolving every item, or a candidate is created by a background flow, there is currently no page to find it again.
- **Deduplication:**
  - Gmail: **real, server-side, wired up.** `api/gmail-check-email.js` calls `listProcessedGmailMessageIds(uid)` (`api/_sourceRecordsStore.js`, reads existing `gmail_email` SourceRecords via the Admin SDK) and filters already-processed message IDs out **before** fetching/extracting them. Tested in `tests/gmail-messages.unit.mjs` and the module-mocked `tests/gmail-check-email-persistence.unit.mjs`.
  - CSV import: client-side exact-match dedupe against already-loaded items (`App.jsx`, `testKey`/`testSet`, title+subject+date).
  - Recurring obligations only: `src/organizer/recurringObligationMatch.js`, wired into `AuthShell.jsx`'s `handleCheckEmail`. Deterministic, filler-stripped exact-title-match + hard gates (type, recurring flag, resolved child/family target) — a match against an existing recurring Item creates a `reviewStatus: "corroborated"` candidate (provenance kept, never enters the review queue, never overwrites the Item's parent-approved schedule); a same-run duplicate is skipped entirely. Tested in `tests/recurring-obligation-match.unit.mjs` (28 assertions).
  - **One-time obligations (assignment/test/quiz/project/school_event/family_event) have no obligation-level reconciliation at all.** "Math Test Friday" re-extracted later as "Math Test Monday" is not detected as a probable date-change/update — it becomes an independent new pending candidate every time. Only the Gmail message-id layer prevents literally re-processing the same email twice; it does not compare obligation content against existing canonical Items.
  - Photo ingestion: no dedupe of any kind (each capture is a distinct, one-off parent action; this is a deliberate, reasonable scope boundary, not an oversight).
- **Idempotency of the commit itself:** `createItem()` uses Firestore `addDoc` (or a guest-local generated id) — there is no deterministic/idempotency key on the write. If a candidate is ever re-submitted while still `"approved"` (not yet `"committed"`), it would create a second Item. No code path does this today, but nothing prevents it either. This matches a gap already tracked internally before this audit (see repository history — "Harden candidate-to-item commit idempotency").

## 9. Security / Trust Boundary

- **Firestore rules** (`firestore.rules`): `users/{uid}` and everything beneath it — read/write iff `request.auth.uid == uid`. This is the **entire** authorization model; there is no Household/Membership check because there is no Household/Membership entity. `gmailConnections/**` and `gmailOAuthStates/**` are explicitly top-level (outside `users/{uid}`) and unreachable by any client rule (`allow read, write: if false`), reachable only by the server's Admin SDK — this is a deliberate, documented, sound boundary.
- **Server endpoints:** every API route except `api/gmail-oauth-callback.js` calls `requireFirebaseUser(req)` (`api/_auth.js`, verifies a real Firebase ID token via the Admin SDK — signature/kid/alg/iss/aud/exp/iat/sub/auth_time). The one exception is legitimate: the OAuth callback is a bare browser redirect with no Authorization header available; it instead trusts only a server-generated, single-use `state` record consumed via `consumeOAuthState()` — no client-supplied uid is ever trusted. Confirmed via `tests/gmail-oauth.unit.mjs` (69 assertions).
- **Client-supplied identifiers are never trusted for uid** anywhere in `api/`: `requireFirebaseUser` explicitly returns only the token's own decoded `uid`.
- **Parent-only admin/ingestion controls are gated behind device-mode + Parent Unlock**, confirmed by three passing Playwright regression suites: `photo-ingestion-guest-gate.playwright.cjs`, `parent-tools-persistence.playwright.cjs`, `parent-page-import-navigation.playwright.cjs`, `child-page-back-navigation.playwright.cjs`.
- **Important caveat (architectural, not a defect):** because parent and child share one Firebase uid, this boundary is enforced **entirely client-side** (localStorage device-mode + PIN check happens in the browser). A user with direct Firestore/API access using that same uid's credentials has full access regardless of "device mode" — there is no second, lower-privilege credential for a child. This matches a single-shared-device household threat model, not a model where the child is assumed to have independent access to Firebase credentials or dev tools.
- **Dependency vulnerabilities** (`npm audit`, 2026-09-20): 4 findings, all dev-time or transitive-only —
  - `esbuild <=0.24.2` (via `vite`) — moderate, dev-server-only CORS issue; no production code path (the built app is static output, `vite`/`esbuild` are not present at runtime).
  - `uuid <11.1.1` (via `gaxios`, a transitive dependency of `firebase-admin`'s toolchain) — moderate; not directly reachable from any code this app writes.
  - No production-reachable vulnerability identified.
- **Ingestion trust model:** every extraction endpoint sanitizes/validates untrusted model output at the boundary (enum checks, regex-validated dates/times, dropped rather than trusted-as-is on any mismatch) rather than trusting the model's JSON directly — confirmed in `api/extract-obligations.js`'s `sanitizeObligation`/`sanitizeObligationsResponse` and covered by 64 unit assertions in `tests/extract-obligations.unit.mjs`.
