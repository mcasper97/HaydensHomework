## Google Calendar Audit (Brief §6)

- **No Google Calendar OAuth, API client, event-mapping, sync, or UI code exists anywhere in the repository.** `googleapis` is not a dependency. The existing `_googleOAuth.js` module requests only `https://www.googleapis.com/auth/gmail.readonly` — it cannot be reused as-is for Calendar write access; a Calendar integration needs its own consent screen, scope (`calendar.events` or similar, least-privilege), and its own server-private token store analogous to `gmailConnections` (a fresh top-level collection, `if false` client rule, Admin-SDK-only access — the existing pattern is directly reusable as a *template*, not as shared storage).
- **No architecture currently treats Google Calendar as a system of record for anything** — there's nothing to flag here today, precisely because nothing has been built yet. The implementation plan must preserve this: Hayden's Homework's own `items` collection stays authoritative; Calendar receives one-way managed publishes only, per spec §5.7.
- **Recommendation for the implementation plan:** store a `googleCalendarEventId` (and a small publish-state enum) directly on the canonical Item — this is the same "one canonical Item + metadata" pattern already used for `schedule` (recurrence) and matches the existing `sourceRecordId` precedent. Do not create a parallel `PublishedEvent` collection unless a concrete reason emerges.

## Study / Readiness Audit (Brief §7)

- **Existing study-adjacent logic:** `study_task` type + `parentItemId` link (manual only, AC-09); `preparationRequired` boolean (manual only); the `App.jsx` WorldMap/flashcards/game/loot subsystem (real, working, but disconnected from source material — see AC-10 evidence above).
- **Smallest reasonable Phase-1-v2 slice, in order of leverage:**
  1. Auto-suggest (not auto-create — matches the ingestion trust model already established everywhere else) a `study_task` at test/quiz creation/approval time, pre-filled and shown in the same review/edit surface already used for recurrence suggestions (`ItemForm.jsx`'s established "opt-in section, parent edits before it's authoritative" pattern is directly reusable).
  2. One new, minimal "practice" surface that takes a `study_task`'s linked assessment's `subject`/`academicTopic`/`academicUnit` (already-stored fields — no new extraction needed) and either (a) reuses the existing vocab/flashcard engine seeded from that topic instead of a parent-typed list, or (b) is a new, deliberately small activity type if the existing engine's assumptions (free-typed word lists, not topic strings) don't fit cleanly — this decision needs a short spike, not a guess, before the plan commits to one path.
  3. A `readiness` field (`"needs_review" | "in_progress" | "ready"`) on the `study_task` (or the assessment it supports), updated from simple evidence (activity completed + a basic correct/incorrect tally) — explicitly not a mastery model.
- **Do not build a general game framework.** The brief and spec both explicitly warn against this, and the existing `App.jsx` game system already demonstrates the team's own instinct to build broad reward/progression mechanics — the plan needs a hard scope line here.

## Security / Trust Review (Brief §8)

| Check | Result |
|---|---|
| Firestore rules enforce per-user ownership | **Pass** — `firestore.rules`, `request.auth.uid == uid` on `users/{uid}/**`; server-private collections (`gmailConnections`, `gmailOAuthStates`) explicitly `if false` to all clients. |
| Parent-only ingestion/admin never exposed as a normal child action | **Pass, with the AC-15 architectural caveat above** (client-side boundary, single shared uid). |
| Server endpoints verify real authenticated identity, not client-supplied ids | **Pass** — every endpoint except the OAuth callback calls `requireFirebaseUser()` (Admin SDK `verifyIdToken`); the callback instead trusts only a server-generated, single-use `state` token. No endpoint accepts a client-supplied uid. |
| External-calendar credentials never exposed to client / never committed | **N/A today** (no Calendar integration exists yet) — but the existing Gmail token pattern (`gmailConnections`, Admin-SDK-only, `if false` client rule, refresh token never returned to the browser) is the correct template to reuse when Calendar is built. |
| Ingestion failures/ambiguity fail safely and visibly | **Pass** — see AC-17. |
| Dependency vulnerabilities, production-reachable vs. dev-only | **No production-reachable vulnerability.** `npm audit`: `esbuild`/`vite` (dev-server-only, moderate) and `uuid` via `gaxios` (transitive, moderate) — both outside any path the built, deployed app executes. |

**Net security assessment: no regression, no new exposure found. The one open architectural question (AC-15's client-side-only boundary) is pre-existing and out of scope for this audit to resolve — it needs an explicit product decision, not a code fix, and should be carried forward rather than silently accepted.**

## Migration Requirements

**None required to complete this audit or to begin the recommended AC-04/AC-05 slices.** Product Spec v2 does not change any existing field's meaning; every gap identified above is additive (a new field, a new collection, a new UI surface) or purely a UI-surfacing gap (AC-04's Review Inbox). The one item requiring care rather than a schema migration: introducing a commit-idempotency key for `createItem()` (AC-05) must not change the existing `EMPTY_DEFAULTS` shape or any already-committed Item — it only needs to affect the *write path*, not stored data.
